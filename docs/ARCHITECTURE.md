# Scrapline — Architecture & Technical Design Document

Этот документ описывает технические решения, архитектурные паттерны и подходы к оптимизации для разработки Scrapline на движке **Godot 4.x**.

## 1. Data-Driven Design (Godot Resources)
Главное правило: **Добавление нового контента (модулей, оружия, врагов) не должно требовать написания нового кода (за исключением уникальных механик).**

Мы используем `Resource` классы в Godot для определения характеристик.

### Пример архитектуры данных:
* `ItemData` (Resource) — Базовый класс для всего, что есть в инвентаре.
  * `ModuleData` (наследует ItemData) — Данные для построек.
    * Поля: `scene_path` (путь к PackedScene), `size` (Vector2i), `base_cost`.
  * `WeaponData` (наследует ModuleData)
    * Поля: `fire_rate`, `base_damage`, `projectile_scene`, `range`.
  * `ModifierData` (наследует ModuleData)
    * Поля: `tags_to_add` (Array[String]), `stat_multipliers` (Dictionary: {"damage": 1.5, "speed": 0.8}).

При создании нового оружия дизайнер просто создает новый `.tres` файл на основе `WeaponData`, настраивает параметры в инспекторе и указывает сцену пули.

### Ресурсы на конвейере
Сам "Ресурс" (Scrap, Энергия), перемещающийся по сетке, в логике представляет собой легковесный объект данных (или словарь/Struct).
* `Payload` (Class):
  * `base_type`: String (Scrap, Biomass)
  * `damage`: float
  * `tags`: Array[String] (e.g., ["Fire", "Explosive", "Piercing"])
Только когда `Payload` попадает в пушку, пушка читает эти теги и применяет их к инстанцируемому `Projectile`.

## 2. Архитектура Сетки (Grid System)
* Сетка — это 2D массив (или `Dictionary` с ключами `Vector2i`).
* Логика сетки (GridManager) отделена от визуализации.
* *Система Линков:* Вместо физической симуляции каждого кусочка конвейера (как в Factorio), здания используют **Graph/Node** подход. Здание знает, кто его сосед, куда направлен выход, и просто передает `Payload` по таймеру (или событию) следующему зданию. Это кардинально экономит CPU на мобилках.

## 3. Оптимизация (Мобилки)
Scrapline предполагает наличие сотен снарядов и десятков работающих зданий.

1. **Object Pooling:** Обязателен для `Projectile` (снарядов), `Enemy` (врагов) и `FloatingText` (цифры урона). `_process` и `queue_free()` сотен пуль убьют сборщик мусора. Пули при попадании прячутся (`hide`, выключают физику) и возвращаются в Pool.
2. **Отказ от `_process` там, где можно:**
   * Здания (Производители/Модификаторы) должны работать по таймерам (Timer node или глобальный TickManager), а не через `delta` в `_process`.
   * Если здание ждет ресурс, оно ничего не делает (idle state, `set_process(false)`), пока не получит сигнал `resource_received`.
3. **Физика против Raycast:**
   * Снаряды вроде пуль/лазеров не должны использовать `RigidBody2D`. Используйте простую кинематику (`position += direction * speed * delta`) и проверяйте пересечения через `Area2D` или ShapeCast/RayCast.
   * Настоящая физика (`RigidBody2D`) нужна только для отбрасывания врагов (Knockback), но и это можно симулировать (Tween/Lerp).
4. **Визуализация ресурсов:**
   * Если на конвейере лежит 50 ресурсов, не нужно делать 50 узлов `Sprite2D` со своими скриптами. GridManager или отдельный Render-менеджер может отрисовывать их через `RenderingServer` (MultiMesh) или легкие `Sprite2D` без скриптов, обновляя позиции массивом.

## 4. Разделение Логики и View (MVC подход)
* **Model:** Данные сетки, инвентаря, HP базы.
* **View:** Анимации, UI, спрайты конвейеров, VFX взрывов.
* **Controller/System:** Менеджеры волн, расчета урона.
* *Почему это важно?* Если босс "отключает" здания, это меняет флаг в Model. View подписывается на сигнал `disabled_changed` и меняет цвет здания на серый. Если логика завязана на цвет пикселей или анимации — проект быстро станет неподдерживаемым.

## 5. Технические Риски и Проверка (Phase 1 Prototypes)

### Риск 1: Производительность логистики (Pathing)
* **Проблема:** Если каждое здание каждый кадр спрашивает "куда мне отдать ресурс?", телефон сгорит.
* **Проверка (Прототип):** Создать сетку 10x10, заполнить роутерами, запустить 500 предметов. Проверить FPS на старом Android-телефоне.
* **Решение:** Кэширование путей. При установке/удалении здания GridManager пересчитывает граф (кто кому передает). В бою маршрут уже известен на 100%.

### Риск 2: Визуальная нечитаемость (Clutter)
* **Проблема:** Десятки пуль, врагов, взрывов и летящих ресурсов превратят экран в кашу.
* **Проверка (Прототип):** Заспавнить 5 пулеметов и 50 врагов. Попробовать понять, откуда летит урон.
* **Решение:** Жесткая иерархия Z-Index и Color Palette. Враги — красные/темные, снаряды игрока — яркие/светящиеся, сетка базы — приглушенная. Мелкие снаряды не должны иметь огромных шлейфов.

### Риск 3: Слишком сложная математика статов (Stacking)
* **Проблема:** `Duplicator` делает 2 ресурса с 50% урона, потом они сливаются `Combiner`'ом, потом умножаются `Enlarger`'ом. Возможны бесконечные циклы или ошибки float.
* **Проверка:** Написать юнит-тест (на GDScript или вне движка) симуляции пути ресурса.
* **Решение:** Использовать плоские/аддитивные бонусы вместо мультипликативных там, где это возможно. Написать анти-loop проверки в графе сетки при фазе строительства (нельзя замкнуть конвейер сам на себя).

## 6. Структура сцен Godot
Рекомендуемая структура:
```
Main.tscn
├── Managers/
│   ├── GameManager
│   ├── GridManager
│   └── WaveManager
├── UILayer/ (CanvasLayer)
│   ├── HUD (HP, Wave, Currency)
│   ├── BuildMenu
│   └── EndScreen
├── World2D/
│   ├── GridMap (TileMapLayer для пола)
│   ├── Buildings/ (Тут инстансятся модули)
│   ├── Enemies/
│   └── Projectiles/ (Object Pool node)
```
